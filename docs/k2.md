# OTLP ingestion through K2

The ingestion Worker accepts OTLP/HTTP JSON and protobuf on `/v1/logs`, `/v1/traces`, and `/v1/metrics`. It validates and normalizes the request, archives its original bytes after gzip decompression to R2, then publishes a small archive pointer to K2. The SDK receives a successful OTLP response only after both writes succeed. R2 or K2 failures return HTTP 503 with `Retry-After: 5`; a failed publish leaves the R2 object available for recovery. A missing producer binding also returns 503.

Both compressed and decompressed request bodies are limited to 8 MiB. The K2 record contains `{version:1,id,signal,key,contentType}`, so large OTLP requests do not encounter K2's roughly 1 MB individual-record limit. Raw archives use `otlp/v1/<signal>/<id>` and have no application expiration.

## Provision a stream and subscription

K2 currently requires Workers Paid. Create a stream with a token holding **K2 Config Write**:

```sh
curl --fail-with-body "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/k2/streams" \
  -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"name":"mvp_o11y","http":{"enabled":false},"worker_binding":{"enabled":true},"retention_seconds":2592000}'
```

Record the returned stream ID. Create a subscription using a token with **K2 Consume**:

```sh
curl --fail-with-body "https://$K2_STREAM_ID.k2.cloudflarestorage.com/subscriptions" \
  -H "Authorization: Bearer $K2_API_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"name":"clickhouse_ingest","start_at":{"type":"earliest"}}'
```

Record `result.id` as `K2_SUBSCRIPTION_ID`. Add a producer binding to Wrangler configuration:

```json
{"k2":[{"binding":"INGEST","stream":"YOUR_32_CHARACTER_STREAM_ID"}]}
```

Set `K2_STREAM_ID` and `K2_SUBSCRIPTION_ID` as Worker variables and `K2_API_TOKEN` as a Worker secret. Apply D1 migration `0002_ingest.sql` before enabling polling. The producer binding authenticates itself; no produce token is required. Public HTTP production remains disabled.

## Polling and batching

Cron invokes `pollK2`. It requests up to ten archive pointers at a time, drains up to four batches, and stops starting further inserts after a 45-second budget. Network requests have timeouts; the ClickHouse client must also bound insertion time. An empty response ends the invocation; the next cron tick supplies the polling backoff. K2 push-based Worker consumers remain on Cloudflare's roadmap.

Every invocation creates a unique `worker_id`. It uses the documented subscription `/consume`, `/batches/<id>/ack`, and `/batches/<id>/nack` HTTP endpoints. K2 owns the checkpoint. A batch is acknowledged only after all its table inserts and D1 receipts succeed. On failure or budget exhaustion, it is released for retry. A failed release falls back to K2's five-minute lease expiration. Partial batches are never acknowledged. Malformed pointers or missing archives fail the batch visibly and need operator repair; they are not silently skipped.

Rows are batched **within each archived OTLP request and destination table**, with a fixed maximum of 5,000 rows per insert. This makes each chunk and its deduplication token stable even when K2 redelivers different batch groupings. Configure the upstream OpenTelemetry Collector's batch processor to produce useful request sizes. At small export sizes, more inserts are expected; cross-request microbatching would need a durable batch manifest before insertion to preserve retry identities.

## Delivery and duplicate handling

The archive ID is a SHA-256 of the signal, media type, and original decoded-compression bytes. A byte-identical retried export, even when gzip transport changes, produces the same ID. Intentionally submitting identical export bytes is treated as the same export; JSON encodings with different whitespace or order receive different IDs. The archive key deliberately excludes the wall-clock date so retries across days retain their identity.

Each request/table/chunk uses `otlp-v1:<archive-id>:<table>:<chunk-index>` as its ClickHouse insertion deduplication token. After a confirmed insert, the Worker writes a permanent D1 receipt. Subsequent attempts skip confirmed chunks. Receipts are written after insertion, never before it. Do not delete them while replay is possible. Chunk size and normalization changes require a versioned archive/receipt migration; changing them in place can invalidate retry identity.

This is **at-least-once delivery**, not an exactly-once transaction across K2, D1, and ClickHouse. If an insert succeeds but its D1 receipt fails, retry safety depends on ClickHouse's finite insertion-deduplication window. Concurrent duplicate exports have the same constraint. An ambiguous insert retried after that window can duplicate rows. ClickHouse `MergeTree` primary keys do not enforce uniqueness. Provision and tune the ClickHouse deduplication window for the expected retry outage, and investigate prolonged receipt failures before replaying old data. A K2 `batch_id` is never used as the deduplication identity because redelivery can replace it.

K2 retention is a buffer, not permanent storage. Unconsumed records expire too. R2 archives remain, but replaying expired pointers currently requires an operator to republish the stored `{version,id,signal,key,contentType}` pointer. Permanent retention requires that the R2 bucket have no expiration lifecycle rule for this prefix; likewise, no TTL should remove the ClickHouse data or D1 receipts. No code automatically deletes these resources.

## Verified public beta limits and references

As documented October 2026: default retention is seven days, configurable from one hour to 30 days; the public beta allows 10 GB account storage. Each stream supports 30 MB/s production, 5 MB produce calls, approximately 1 MB per record, 10 MB consume responses, up to 10,000 requested records, and 128 concurrent leases per subscription. Production writes are atomic; consumers must handle duplicates.
